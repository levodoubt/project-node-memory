# 1.5.14

技能文档瘦身：`SKILL.md` 从 12079 字符降到约 5000，明细搬进同目录的 `references/`，按需加载。

## 为什么

`SKILL.md` 每被加载一次就整段进上下文。1.5.13 时它已经 12079 字符，其中「边界规则与实现细节」「命令行命令表」「`rules.json` 用法」这类**一年调一次**的内容占了三分之一以上，却和「写入三条铁律」一样，每次都要付一遍 token。写库时真正每次都用到的是很小的一撮。

## 怎么拆

- `SKILL.md` 只留：什么时候该写、先读再写、目录规划、TID 与两种引用的核心规则、写入三条铁律、改名、诊断三档 + 阈值、建库与注册、两条「去哪看明细」的入口。
- `references/` 六份，按「问题出现时才会翻」分：

  | 文件 | 内容 |
  | --- | --- |
  | `syntax.md` | TID 全规则、属性缺省、行内定义、代码区、渲染上限 |
  | `write.md` | `kb_write` 全部限制、`target` 判定、校验两层、四道拦截 |
  | `diag.md` | 三档细节、advice 阈值与判据、豁免表、TID 文本核对 |
  | `cli.md` | `nodekb` 命令表、`--json`、退出码、批量改名计划文件 |
  | `rules.md` | `rules.json` 的语义与现成配置 |
  | `changes.md` | 版本升级说明：从已推送的 1.5.8 到当前版本，每版对用库的人有什么影响 |

- `SKILL.md` 末尾有一张「需要时读哪份」的索引表，避免模型猜。

## 让 references 真的读得到

宿主只有在技能带 `resourceBase` 时才会把目录告诉模型（否则渲染成「资源由 provider 管理」，相对路径无从解析）。所以 `lib/host/skill.js` 注册时补上：

```js
resourceBase: { kind: 'directory', path: <skills/project-node-memory-guide 的绝对路径，斜杠统一> }
```

用配置项 `skill.text` 覆盖正文时**不带** `resourceBase`（那时正文和磁盘上的 `references/` 未必对得上）。新增 `bundledSkillDir()` 导出。

## 文案

`SKILL.md` 正文本身重写过（不是删减），所有硬规则都保留：TID 不要求含冒号、`###` 不建节点、`mode=node` 不带标题行、围栏与行内代码不解析、只改大小写的改名、`rules.json` 是声明式检查。

工具描述与参数描述按「不重复技能、不写经验教训」收紧了一遍：

- `format` 参数（5 个工具共用）：「（Agent 做条件判断用，省得再解析文本）」→「（可用于条件判断，省去解析）」。
- `kb_list`：删掉「路径已不存在的登记不占版面，只在末尾报一行总数」。
- `kb_read`：描述只留「读一个节点 + 分窗读 + `format=json`」，`target` / `mode` / `find` 的说明交给参数描述（原来两处重复）。
- `kb_search`：「片段是渲染过的…不用再读一次定义」→「片段经过渲染…不用再读定义」。
- `kb_diag`：warnings 一档不再罗列内部规则种类（那是 `references/diag.md` 的事）。
- `kb_rename`：删掉「新名字 slug 化后撞上已有 TID 会拒绝」与「只改大小写也可以」两句；`new_name` 删掉「（旧实现会静默改名失败却报成功）」。
- `kb_init`：「已经有 .nodekb/ 就别调」→「已有 .nodekb/ 就别调」。

新文案先落在工作区唯一的 `审阅稿.md` 里由人改，再落回源码（流程见 KB `todo/001-pending.md`）。
